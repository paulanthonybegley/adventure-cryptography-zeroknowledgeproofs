# Verus Formal Verification Plan: Bank Trust-less Bridge

This document explains the formal verification strategy for the **Bank Trust-less Bridge** using Verus and SMT solvers.

---

## 🛠️ Verification Strategy

We use **Verus** (a verified Rust dialect) to prove that the implementation matches its mathematical specification. This eliminates entire classes of bugs (overflows, memory safety, logic errors).

### 1. Frontend (Identity Layer)
- **Goal:** Prove that a valid signature can only be generated by a user who knows the private key.
- **Spec:** [frontend.rs.verus](file:///Users/paulbegley/Documents/lego-crypt-foundation-zkp/bank-integration-architecture/verus-specs/frontend.rs.verus)
- **Invariant:** `pub_key == g.pow(priv_key) % p`. Verus ensures this relationship holds for all verified operations.

### 2. Engine (Batching Layer)
- **Goal:** Prove Merkle path integrity and correct polynomial evaluation.
- **Spec:** [engine.rs.verus](file:///Users/paulbegley/Documents/lego-crypt-foundation-zkp/bank-integration-architecture/verus-specs/engine.rs.verus)
- **Invariant:** Every step in the Merkle proof must reconstruct the parent hash. Verus uses recursion induction to prove this for trees of any depth.

### 3. Shield (Privacy Layer)
- **Goal:** Prove the correctness of the Homomorphic Addition.
- **Spec:** [shield.rs.verus](file:///Users/paulbegley/Documents/lego-crypt-foundation-zkp/bank-integration-architecture/verus-specs/shield.rs.verus)
- **Invariant:** `decrypt(encrypt(A) + encrypt(B)) == A + B`. Verus proves this algebraic identity holds, ensuring the banking audit is mathematically sound despite the encryption.

### 4. Guard (Fairness Layer)
- **Goal:** Prove that the verification logic matches the sequential computation logic.
- **Spec:** [guard.rs.verus](file:///Users/paulbegley/Documents/lego-crypt-foundation-zkp/bank-integration-architecture/verus-specs/guard.rs.verus)
- **Invariant:** The VDF requires a chain of squaring operations that cannot be bypassed. The spec ensures that the `verify` function is a faithful check of the `compute` result.

### 5. Backend (Infrastructure Layer)
- **Goal:** Ensure the vault balance never drops below zero and only updates upon valid proof.
- **Spec:** [backend.rs.verus](file:///Users/paulbegley/Documents/lego-crypt-foundation-zkp/bank-integration-architecture/verus-specs/backend.rs.verus)
- **Invariant:** `balance >= 0`. This is the "Safety Invariant." Verus checks every code path in the `Backend` to ensure this is never violated.

## 🚀 Execution
To run these verifications in a real environment:
1.  Install the **Verus** toolchain and **Z3** SMT solver.
2.  Run `verus <file>.rs` on each annotated module.
3.  The solver will either output `Verification successful` or provide a counter-example where the math fails.
